1. Quick start and shared conventions

Base URL

const baseURL = 'http://10.10.26.198:5000/api/v1';

Use the deployment URL in staging/production. Do not append a trailing slash. All endpoint paths below are relative to /api/v1.

Authentication header

After admin login, send the access token on every protected request:

Authorization: Bearer <accessToken>
Content-Type: application/json
Never expose SUPER_ADMIN_PASSWORD, JWT secrets, Stripe keys, or refresh tokens in frontend source code. Store tokens using the dashboard's secure session strategy.

Standard success envelope

{
  "success": true,
  "message": "Human-readable result",
  "pagination": { "page": 1, "limit": 10, "totalPage": 3, "total": 26 },
  "data": []
}

pagination appears only on paginated endpoints. data may be an object, array, or null.

Standard error envelope

{
  "success": false,
  "message": "Validation Error",
  "errorMessages": [
    { "path": "email", "message": "Invalid email" }
  ]
}
StatusMeaningDashboard behavior
400Invalid body or invalid state transitionShow field/state error; do not retry automatically.
401Missing, invalid, or expired access tokenTry token refresh once, then redirect to admin login.
403Authenticated but insufficient roleShow “not authorized”; hide the action in the UI.
404Resource does not existShow not found and refresh the list.
409Conflict, often payment/payout readinessShow the server message and refresh current data.
429Rate limit exceededDisable submission temporarily.
500Server or external provider failureShow a generic retry message and retain form state.

Pagination, filtering, sorting, and field selection

List endpoints backed by the common query builder support these query parameters:

pagepage=21-based page; default 1.

2. Authentication

POST/auth/admin/login

Public Password login for ADMIN and SUPER_ADMIN only.

Body

{
  "email": "admin@example.com",
  "password": "your-admin-password"
}

200 response

{
  "success": true,
  "message": "Admin logged in successfully.",
  "data": {
    "accessToken": "eyJhbGciOi...",
    "refreshToken": "eyJhbGciOi..."
  }
}

Common failures: account missing/unverified/banned, non-admin account, or incorrect password.

POST/auth/refresh-token

Public with refresh token Generates a new access token. Rotate the in-memory/current access token after success.

Body

{ "refreshToken": "eyJhbGciOi..." }

200 response

{
  "success": true,
  "message": "Access token generated successfully",
  "data": { "accessToken": "eyJhbGciOi..." }
}

Recommended frontend token flow

  1. Log in through /auth/admin/login.
  2. Attach Authorization: Bearer ... to protected requests.
  3. On the first 401, call /auth/refresh-token once and replay the original request.
  4. If refresh fails, clear local authentication state and redirect to admin login.
  5. There is currently no backend logout/token-revocation endpoint; logout is client-side token removal.

ADMIN / SUPER_ADMIN Starts/retries the seller Stripe transfer. No request body.

Requirements

  • Order status must be verification or payout_processing.
  • Buyer payment must be paid.
  • Seller must have a connected Stripe account with onboarding complete and payouts enabled.

200 response

{
  "success": true,
  "message": "Seller payout marked as paid",
  "data": {
    "_id": "66dd44444444444444444444",
    "orderNumber": "CLT-12345678901",
    "status": "verification",
    "payoutStatus": "paid",
    "payoutTransferId": "tr_...",

Possible conflict: seller has no connected Stripe account, onboarding is incomplete, or payouts are disabled.

POST/issues

ADMIN / SUPER_ADMIN Opens an issue for a product. Only one unresolved issue may exist per product.

Body

{
  "productId": "66cc33333333333333333333",
  "issueType": "verification_failed",
  "reason": "Serial number does not match the proof document"
}

Allowed issueType: buyer_refused or verification_failed.

201 response

{
  "success": true,
  "message": "Issue created successfully",
  "data": {
    "_id": "66ff66666666666666666666",
    "product": "66cc33333333333333333333",
    "buyer": "66ee55555555555555555555",
    "seller": "66bb22222222222222222222",
    "admin": "66aa11111111111111111111",
    "issueType": "verification_failed",
    "reason": "Serial number does not match the proof document",
    "resolved": false
  }
}
If the associated order was paid, creating an issue automatically refunds the buyer. If the seller was already paid, the Stripe transfer is reversed first. The seller is emailed.

PATCH/issues/:id/resolve

ADMIN / SUPER_ADMIN Resolves an open issue and applies the selected product action.

Body: delete product

{ "action": "delete" }

Body: relist product

{ "action": "make_available" }

200 response

{
  "success": true,
  "message": "Issue resolved successfully",
  "data": {
    "_id": "66ff66666666666666666666",
    "product": "66cc33333333333333333333",
    "issueType": "verification_failed",
    "reason": "Serial number mismatch",
    "resolved": true,
    "updatedAt": "2026-08-03T10:00:00.000Z"
  }
}

delete removes the product and S3 assets. make_available clears the buyer and relists the product. Both actions notify the seller by email.

8. Health checks and implementation notes

GET/health/live

Server process health; this path is outside /api/v1.

{ "status": "ok" }

GET/health/ready

Returns 200 when MongoDB is connected, otherwise 503; this path is outside /api/v1.

{ "status": "ready" }

Dashboard implementation recommendations

  • Centralize the base URL and bearer-token injection in one HTTP client.
  • Use one refresh queue so simultaneous 401 responses do not trigger multiple refresh calls.
  • Drive order action buttons from the allowed-transition table, then still handle server-side 400/409 responses.
  • After status, payout, issue, product update, or deletion mutations, invalidate/refetch the affected list and detail queries.
  • Show destructive confirmation dialogs for account deletion, product deletion, and issue resolution with delete.
  • Display monetary values using the product/order currency configured for the project; backend numeric values are major currency units.
  • Treat server response messages as user-facing context, but do not depend on exact text for application logic.
