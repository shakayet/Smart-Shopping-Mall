1. Quick start and API conventions

1.1 Base URL and headers

Base URL: https://your-api-host.example/api/v1
Accept: application/json
Content-Type: application/json
Authorization: Bearer <accessToken>

All protected admin routes accept a JWT access token in the HTTP Authorization header. Role claims must be exactly ADMIN or SUPER_ADMIN. These two roles currently have identical route permissions.

Token storage. The API returns tokens in JSON and does not set an HttpOnly authentication cookie. If a same-origin backend-for-frontend is available, keep tokens in secure HttpOnly cookies there. Otherwise keep the access token in memory and protect refresh-token storage carefully.

1.2 Success envelope

{
  "success": true,
  "message": "Human-readable message",
  "pagination": { "total": 42, "limit": 10, "page": 1, "totalPage": 5 },
  "data": {}
}

message, pagination, and data may be omitted by JSON serialization when undefined. List endpoints in this guide return the row array directly in data; they do not wrap it in { result, meta }.

1.3 Error envelope

{
  "success": false,
  "message": "Validation Error",
  "errorMessages": [
    { "path": "email", "message": "Invalid email" }
  ]
}

In non-production environments, an additional stack property may appear. A route miss returns 404 with the same general shape and an errorMessages[0].path equal to the requested URL.

1.4 Common status codes

CodeMeaning and frontend action
200 OKSuccessful read, update, login, or delete.
201 CreatedProduct or issue created.
400 Bad RequestSchema validation or business-rule failure. Render errorMessages and refresh stale workflow data when relevant.
401 UnauthorizedMissing, invalid, or expired token. Try one refresh; then return to sign-in.
403 ForbiddenAuthenticated role lacks permission.
404 Not FoundRequested product, order, issue, or route does not exist.
409 ConflictExternal/state conflict, notably unavailable Stripe payout onboarding.
413 Payload Too LargeUpload exceeds configured maximum.
429 Too Many RequestsRate limit reached. Respect RateLimit/Retry-After response headers.
500 Internal Server ErrorUnexpected failure or failed third-party operation. Do not assume a mutation was rolled back; refetch the resource.

1.5 Pagination, filtering, sorting, and projection

QueryBehaviorSupported by
pagePositive numeric page; backend default 1. Invalid/zero values fall back to 1.Users, products, admin orders
limitNumeric page size; backend default 10. No explicit maximum is enforced.Users, products, admin orders
sortMongoose sort expression. Default -createdAt; examples: price, -price, name.Users, products, admin orders
searchTermCase-insensitive regex search. Users: name/email/contact. Products: name/brand/description.Users, products only
fieldsComma-separated projection such as name,email,status. Default excludes __v.Users, products only
Other keysExact Mongo field filters. Useful examples: role=USER, status=active, status=verification, payoutStatus=failed.Users, products, admin orders
Do not pass UI-only query keys. Unknown keys on filter-enabled endpoints become database equality filters and may produce an empty list. Remove values such as tab, view, or search; the search key is specifically searchTerm.

Issues are currently returned as one unpaginated, newest-first array; query parameters are ignored.

2. Authentication and account recovery

POST/auth/admin/login

Purpose: Password sign-in for ADMIN and SUPER_ADMIN accounts.

Authentication: Public. Rate limited to 10 attempts/IP/15 minutes.

Body fieldTypeRequiredDescription / validation
emailstringYesValid email syntax. The lookup uses the submitted value; normalize to lowercase in the client.
passwordstringYesNo route-level minimum; stored passwords use a six-character model minimum.

Sample request

POST /api/v1/auth/admin/login
Content-Type: application/json

{ "email": "admin@example.com", "password": "correct-horse-battery-staple" }

200 response

{
  "success": true,
  "message": "Admin logged in successfully.",
  "data": {
    "accessToken": "<jwt>",
    "refreshToken": "<jwt>"
  }
}
ErrorWhen
400Account absent, unverified, banned, or password incorrect.
403The credentials belong to a USER; password login is admin-only.
429Login rate limit exceeded.
After login, call GET /user/profile. The token response does not include name, image, or account details.

POST/auth/refresh-token

Purpose: Exchange a valid refresh token for a new access token.

Authentication: Public endpoint; refresh token is in the JSON body, not the Authorization header.

Body fieldTypeRequiredDescription
refreshTokenstringYesJWT returned by login.
POST /api/v1/auth/refresh-token
Content-Type: application/json

{ "refreshToken": "<refresh-jwt>" }

200 response

{
  "success": true,
  "message": "Access token generated successfully",
  "data": { "accessToken": "<new-access-jwt>" }
}

Errors: 400 missing body field; 401 invalid/expired token, deleted user, banned account, or unverified account. The refresh token is not rotated.

POST/auth/change-password

Purpose: Change the signed-in admin’s password.

Authentication: Bearer access token. Route permits ADMIN and USER, but currently omits SUPER_ADMIN.

Body fieldTypeRequiredRules
currentPasswordstringYesMust match stored password.
newPasswordstringYesMust differ from current password.
confirmPasswordstringYesMust equal newPassword.
POST /api/v1/auth/change-password
Authorization: Bearer <accessToken>
Content-Type: application/json

{
  "currentPassword": "old-password",
  "newPassword": "new-long-password",
  "confirmPassword": "new-long-password"
}

200 response

{ "success": true, "message": "Your password has been successfully changed" }

Errors: 400 validation, user absent, incorrect current password, password reused, or confirmation mismatch; 401 invalid token; 403 role denied.

Backend caveat: A SUPER_ADMIN token receives 403 on this route even though it can use other admin routes.

2.1 Password-recovery sequence

The recovery flow is a three-request sequence. The six-digit OTP expires after 3 minutes; the reset token returned after OTP verification expires after 5 minutes and is single-use.

POST/auth/forget-password

Purpose: Email a password-reset OTP. Public; 10 requests/IP/15 minutes.

Body: { "email": "admin@example.com" } where email is required and must be valid.

200 response

{
  "success": true,
  "message": "Please check your email. We have sent you a one-time passcode (OTP)."
}

Errors: 400 invalid email or user absent; 429 rate limit.

POST/auth/verify-email

Purpose: Verify the reset OTP and obtain a one-time reset token. This endpoint also serves account email verification.

Body fieldTypeRequiredDescription
emailstringYesValid email.
oneTimeCodenumberYesNumeric OTP; send as a JSON number, not a string.
POST /api/v1/auth/verify-email
Content-Type: application/json

{ "email": "admin@example.com", "oneTimeCode": 123456 }

200 reset-flow response

{
  "success": true,
  "message": "Verification Successful: Please securely store and utilize this code for reset password",
  "data": "<one-time-reset-token>"
}

If the account was not yet verified, the same request verifies it and returns no reset token. Errors are 400 for missing/incorrect/expired OTP or absent user, and 429 for the auth rate limit.

POST/auth/reset-password

Purpose: Set a new password using the reset token.

Authentication: Authorization: Bearer <one-time-reset-token>. This is not an access JWT.

Body fieldTypeRequiredRules
newPasswordstringYesConfirmation must match.
confirmPasswordstringYesMust equal new password.
POST /api/v1/auth/reset-password
Authorization: Bearer <one-time-reset-token>
Content-Type: application/json

{ "newPassword": "new-long-password", "confirmPassword": "new-long-password" }

200 response

{ "success": true, "message": "Your password has been successfully reset." }

Errors: 400 missing fields or mismatch; 401 missing, invalid, expired, already-consumed, or unauthorized reset token.

Purpose: Update the signed-in admin’s basic profile and optional image.

Authentication: Bearer token; all known roles.

Content type: multipart/form-data. Send a JSON string in field data and optionally one file in field image.

data JSON fieldTypeRequiredDescription

PATCH/products/:id

Purpose: Edit product metadata or moderation status.

Authentication: Bearer token; all roles. Service authorizes the seller or either admin role.

JSON body fieldTypeRequiredValidation
namestringNoFree-form.
brandstringNoFree-form.
descriptionstringNoFree-form.
pricenumberNoMust be JSON number.

PATCH /api/v1/products/66c0f1234567890123456110

200: Updated product in data. Errors: 400 validation; 401/403 auth/ownership; 404 absent product.

DELETE/products/:id

Purpose: Permanently remove a product and its object-storage image/proof.

Authentication: Bearer token; seller or either admin role.

DELETE /api/v1/products/66c0f1234567890123456110
Authorization: Bearer <accessToken>

200 response

{ "success": true, "message": "Product deleted successfully", "data": null }

Errors: 401/403 auth/ownership; 404 absent product; 500 object-storage/database failure.

Deletion is hard and does not check for an associated order. For verification failures, use the issue-resolution flow so refunds/reversals and seller notification happen first.

5.1 Order status state machine

Current statusPermitted next status(es)Side effects
pending_paymentsecuredNormally entered automatically by Stripe webhook, not by admin.
securedcollection_pending, cancelledCancel refunds paid payment and relists product.
collection_pendingcollected, cancelledCancel refunds and relists.
collectedverificationNo external side effect.
verificationpayout_processing, refundedPayout transition sends Stripe transfer; refund relists product.
payout_processingready_for_deliveryNo new transfer; payout should already be paid.
ready_for_deliverydeliveredProduct becomes sold.
deliveredcompletedProduct remains sold.
completed, refunded, cancelledNoneTerminal states.

PATCH/orders/:id/status

Purpose: Advance an order through the controlled operations workflow.

Authentication: Bearer token; ADMIN or SUPER_ADMIN.

Body fieldTypeRequiredDescription
statusenumYesOne of the 11 lowercase order statuses shown in the state machine.
notestringNoOperations note appended to status history.
PATCH /api/v1/orders/66d0f1234567890123456220/status
Authorization: Bearer <accessToken>
Content-Type: application/json

{ "status": "payout_processing", "note": "Authentication passed" }

200 response

{
  "success": true,
  "message": "Order status updated successfully",
  "data": {
    "_id": "66d0...220",
    "status": "payout_processing",
    "payoutStatus": "paid",
    "payoutTransferId": "tr_...",
    "statusHistory": [{
      "status": "payout_processing",
      "note": "Authentication passed",
      "changedAt": "2026-07-30T11:00:00.000Z",
      "changedBy": "66a0...001"
    }],

Errors: 400 invalid enum/transition, unsettled buyer payment, or payout attempted outside verification; 401/403 auth; 404 order absent; 409 seller has no connected Stripe account or onboarding/payout capability is incomplete; 500 Stripe refund/transfer failure.

Payout behavior: Moving verification → payout_processing immediately calls Stripe. On transfer success, payoutStatus becomes paid; on failure it becomes failed, the order status remains verification, and the request errors. Refetch after every failure.

PATCH/orders/:id/payout

Purpose: Retry or explicitly initiate the seller Stripe transfer for an order in verification or payout_processing.

Authentication: Bearer token; ADMIN or SUPER_ADMIN. No request body.

PATCH /api/v1/orders/66d0f1234567890123456220/payout
Authorization: Bearer <accessToken>

200 response

{
  "success": true,
  "message": "Seller payout marked as paid",
  "data": {
    "_id": "66d0...220",
    "status": "verification",
    "payoutStatus": "paid",
    "payoutTransferId": "tr_...",
    "...": "..."
  }
}

Validation/business logic: Buyer payment must be paid; order status must be verification or payout_processing; seller’s connected account must have submitted details and enabled payouts. If already paid, the call is idempotent and returns the order without another transfer.

Errors: 400 state/payment ineligible; 401/403 auth; 404 order absent; 409 Stripe account unavailable/incomplete; 500 transfer failure.

Despite the response wording, this endpoint does not merely mark a manual payment. It creates a real Stripe transfer.

    "updatedAt": "2026-07-30T12:00:00.000Z"

Business logic: Only one unresolved issue per product. If a paid order is found, any paid seller transfer is reversed first, then the buyer payment is refunded, the order becomes refunded, and status history is appended. The seller is emailed after the issue is created.

Email sending is awaited after issue creation. An email failure can make the HTTP request return 500 even though financial actions and/or the issue database write already occurred. Always refetch issues and the order before offering a retry.

PATCH/issues/:id/resolve

Purpose: Close an unresolved issue by deleting or relisting its product.

Authentication: Bearer token; ADMIN or SUPER_ADMIN.

Body fieldTypeRequiredDescription
actionenumYesdelete or make_available.
PATCH /api/v1/issues/66e0f1234567890123456330/resolve
Authorization: Bearer <accessToken>
Content-Type: application/json

{ "action": "make_available" }

200 response

{
  "success": true,
  "message": "Issue resolved successfully",
  "data": {
    "_id": "66e0...330",
    "product": { "_id": "66c0...110", "name": "Classic Flap Bag", "...": "..." },
    "issueType": "verification_failed",
    "reason": "Serial number could not be authenticated",
    "resolved": true,
    "...": "..."

}

Action behavior: delete deletes the product’s object-storage files and database record. make_available sets product status to available and clears its buyer. Both email the seller, mark the issue resolved, and clear product-list cache.

Errors: 400 invalid action or already resolved; 401/403 auth; 404 issue/product absent; 500 storage/email/database failure.

The adminId passed to the service is not stored as a resolver/audit field. Resolution is not transactionally atomic; refetch after an error.

7.2 Frontend request policy

  1. Attach Bearer <accessToken> to protected requests.
  2. On the first 401, run one shared/single-flight refresh request using the refresh token in JSON body.
  3. Retry the original request once with the new access token. If refresh fails, clear auth state and return to login.
  4. Never automatically retry non-idempotent product, issue, status, or payout mutations after a network/500 response. Refetch first.
  5. Debounce user/product search and use the exact searchTerm query key.
  6. For multipart requests, let the browser create the Content-Type boundary.
  7. Disable workflow actions while pending and refetch order/product/issue data after any mutation.

7.4 Integration acceptance checklist

  • Login stores both tokens and immediately loads /user/profile.
  • One refresh request services concurrent 401 responses; each original request retries at most once.
  • Admin routing checks uppercase role values exactly.
  • Tables consume data as the row array and pagination as metadata.
  • Empty UI filters are removed instead of sent as query parameters.
  • Order controls are derived from the state-transition table, not from a free-form status dropdown.
  • Payout and issue actions display consequences and require confirmation.
  • Mutation errors trigger a resource refetch before a retry is offered.
  • Product and profile upload validation mirrors MIME, signature, and configured size constraints.
  • Unsupported capabilities listed above are not represented as working controls.
